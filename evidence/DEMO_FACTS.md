# Technical facts for the demo and judge questions

This is a technical reference for Opus's storyboard/submission work, not a final pitch or submission. Numbers below refer to the immutable experimental synthetic release `e1-aura-001`. Pending review work must not silently replace reviewed main.

| Likely question | Supported answer | Evidence |
|---|---|---|
| What does it actually let a planner do? | Rank inferred weekday-morning area-to-area flows for further investigation; explore released line/hour and daily counts. It does not optimise routes or establish unmet demand, crowding or capacity. | `../planning/INTERFACES.md`, `e1/e1.json` |
| What leaves the private environment? | Nine allowlisted bundle files containing fixed aggregate tables, public geography, definitions and provenance. No individual tap rows, card IDs or exact event timestamps. Synthetic demo evidence is separate and includes exact reference results; it is not a protected real-data export. | `../pipeline/artifact.py`, `../releases/e1-aura-001/` |
| What is the AI doing? | Optional model translates a question into a typed request. Validation and deterministic execution produce every factual answer from released counts. The scanner is rule-based. Offline presets work without model credentials. | `../web/src/assistant/intent.ts`, `../web/server/assistant.mjs`, O-012 |
| Why not just remove names? | In the supplied native test, four stop/hour sightings single out 97.0% / 97.4% / 90.4% of tested cards under B0/B2/B2-k. This is an empirical lookup attack on row-level representations. No comparable row search exists in RouteSafe output, which does not imply zero inference risk. | `e4/trajectory.json` |
| What is protected by epsilon? | One card's whole stated-period records under add/remove adjacency. With all other cards fixed, output event probabilities differ by at most exp(1) between datasets differing by that card. Replacing its entire history takes two adjacency steps. A person with multiple cards is a group, not automatically one protected unit. | `../privacy/README.md`, `identity/multiple-cards.json` |
| How do caps affect useful counts? | Each card contributes at most 32 OD trips, 64 line/hour boardings, 64 daily taps. OD capping removes 12.15% of the exact inferred trip total. Noise can move individual cells in either direction. Destination inference and contribution loss are separate from mechanism noise. | `e1/e1.json`, `e3/strata.json` |
| Why claim useful if the scores fail? | The narrower morning top-three decision survives: same set in 100/100 diagnostic draws. Fine-grained utility does fail: area WAPE 25.1%, and native MOB-U1 / adapted U2 / adapted U3 scores 0 / 0 / .772. Say the prototype supports that narrower synthetic shortlist, not full MOB-S1 utility acceptance. | `e3/initial-policy-100.json`, `e5/benchmark.json` |
| Why do different error figures disagree? | WAPE weights errors by count volume. MOB-U1 uses equal weight across qualifying cells and clips its score to zero above 50% MAPE. The same artifact has 25.1% WAPE and 55.7% qualifying-cell MAPE. Municipality 14.2% WAPE measures a different, coarser derived table. | `e5/benchmark.json`, `e3/municipality-postprocessing.json` |
| Did you pick a lucky release? | The release was retained unchanged. A predeclared eight-policy development search found no all-target winner. Repeated diagnostics are synthetic experiments, not alternate releases to select for publication. | `e3/policy-search-spec.json`, `e3/policy-search.json`, immutable manifest |
| Is the scanner general-purpose or perfect? | No. Its development score uses known catalog labels. Independent small adversarial probes test abstention and review behavior, not population accuracy. Its labels never authorise export: a separate fixed publisher allowlist does. | `e1s/opus-handoff-review.json`, `e6/scanner-isolation.json` |
| Can retries quietly spend more privacy budget? | The local ledger reserves before drawing and serialises competing publishers. Identical retries return the original result; interrupted attempts stay charged. It is an accidental-repeat guard, not protection against an operator deleting files or deliberately changing software. | `../tests/privacy/test_accounting_processes.py`, `../tests/privacy/test_publisher.py` |
| Is the result audited, anonymous under law or production ready? | Critical code paths received reciprocal builder review and executable checks. That is not independent professional audit, legal certification or a final production policy. The original artifact's pending_review field stays immutable; later code-review records are external. | `e6/opus-privacy-review.json`, `../planning/DECISIONS.md` |
| What survives without internet? | Downloaded static files served locally, schematic map, views, filters, presets and downloads. Street tiles and optional cloud-model translation need network access. Offline reload needs a local server; no public deployment exists. | `e6/integrated-package.json`, `../ROUTESAFE_DEVELOPMENT.md` |

## New results awaiting review

E7 (`e7/membership.json`) simulates exact discrete-Laplace outputs for three preselected fixed neighbouring dataset pairs with all other contributions known. Likelihood-ratio AUC .603/.569/.592; true-positive rates 1.65%/1.52%/2.30% at separately calibrated thresholds with actual false-positive rates .92%/.93%/1.07%. This is not an attack on repeated copies of the original artifact, a general attacker benchmark or a zero-risk proof. Keep it out of final UI claims until reviewed.

The new uncertainty UI at Opus 14d7874 also awaits corrections and review. A marginal ±161 bound for a prechosen OD cell does not give 95% coverage for a top-ranked cell selected using the noisy data. Simultaneous bounds or an explicit selection-aware treatment are needed; see `e6/selected-interval-review.json`. Preserve the reviewed UI's unavailable-interval fallback until this is resolved.
